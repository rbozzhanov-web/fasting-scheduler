# Fuel Window v25 — дизайн полного пакета улучшений

Дата: 2026-09-01  
Ветка: `codex/fuel-window-v25`  
Базовый коммит: `a4c09218ec32685e3b790b759e2e238d2152df03`

## Цель

Повысить надёжность и безопасность Fuel Window, добавить счётчик времени, прошедшего с открытия окна питания, и сохранить текущую простоту интерфейса. Изменения не добавляют новые пользовательские разделы, графики, журналы питания, сервер или обязательную регистрацию.

## Объём

В пакет входят:

1. Счётчик времени с открытия окна питания.
2. Безопасное удаление данных приложения.
3. Нормализация локального состояния и защита запуска от повреждённых данных.
4. Строгая проверка резервной копии.
5. Отказ от постоянного хранения исходного PDF.
6. Усиление roster-парсера и обработка частичных результатов.
7. Исправление жизненного цикла и области очистки service worker.
8. Улучшение доступности без изменения визуального дизайна.
9. Синхронизация README с фактическими возможностями.
10. Автоматические тесты и GitHub Actions.

## Не входит

- История циклов голодания.
- Учёт отдельных приёмов пищи.
- Новые графики и экраны.
- AI-шлюз или AI-пояснения.
- Серверные Web Push-уведомления.
- Новый дизайн приложения.
- Поддержка произвольных форматов roster, не похожих на текущий Air Astana PDF.
- Выбор лицензии репозитория: это отдельное решение владельца.

## Пользовательский сценарий таймера

Существующий главный таймер используется повторно.

- В фазе `idle` он показывает выбранный режим, как сейчас.
- В фазе `fast` он показывает время до открытия окна питания.
- В фазе `eat` он показывает время, прошедшее с открытия окна: `HH:MM:SS`.
- Подпись в фазе `eat`: «С начала окна питания».
- Нижняя строка продолжает показывать точное время закрытия окна.
- В фазе `over` сохраняется текущее поведение.
- Новые кнопки, карточки, настройки и сохраняемые поля не создаются.
- Расчёт выполняется по абсолютным timestamp, поэтому смена часового пояса не сбрасывает счётчик.

## Архитектура

Приложение остаётся статической PWA без сборки и runtime-зависимостей. Для тестируемости небольшая чистая логика выносится из большого inline-скрипта в `app-core.js`.

`app-core.js` отвечает за:

- определение фазы цикла и временных значений;
- нормализацию локального состояния;
- проверку и миграцию backup;
- безопасные ограничения значений;
- экспорт функций в браузер и Node.js-тесты без дублирования логики.

`index.html` остаётся владельцем DOM, событий и отображения.

`roster-parser.js` разделяется логически на извлечение текста из PDF и чистое преобразование элементов страницы в roster. Чистая часть становится доступной тестам.

`circadian.js` сохраняет публичный API, но получает совместимый экспорт для Node.js-тестов.

Никакого bundler или framework не добавляется. Тесты используют встроенный `node:test`.

## Локальное состояние и миграция

Ключ `fuel-v4` сохраняется, чтобы не потерять существующие данные.

При запуске:

1. Значение читается внутри `try/catch`.
2. Некорректный JSON заменяется безопасным состоянием по умолчанию.
3. Известные поля нормализуются по типам и диапазонам.
4. Некорректные элементы `days` и `metrics` отбрасываются отдельно, не уничтожая весь массив.
5. Неизвестные поля не используются интерфейсом.
6. После успешной нормализации состояние сохраняется в каноническом виде.

Допустимые режимы: `12`, `14`, `16`, `18`. Допустимые цели: `fat`, `keep`. Даты roster должны соответствовать `YYYY-MM-DD`; время — `HH:MM`; процент жира и вес используют существующие границы формы.

## Backup

Новый экспорт имеет обёртку `{app:"fuel-window", v:2, saved, state}`.

Импорт поддерживает существующий формат `v:1` и новый `v:2`.

До записи проверяются:

- идентификатор приложения и поддерживаемая версия;
- тип корневого состояния;
- режим, цель и контекст;
- структура завтрака;
- массивы roster и замеров;
- формат дат, времени, кодов и аэропортов;
- числовые диапазоны;
- допустимая длина массивов и строк.

Импорт либо полностью проходит нормализацию, либо не меняет текущее состояние. Сообщение об ошибке объясняет проблему без вывода технического стектрейса.

Roster-кнопки создаются DOM-методами с `textContent`; импортированные строки не вставляются в HTML-атрибуты через конкатенацию.

## PDF и roster

Исходный PDF обрабатывается локально и после разбора не сохраняется в IndexedDB. Старую базу `fuel-pdf` приложение удаляет при очистке данных; отдельная автоматическая миграция не требуется.

Импорт выполняется транзакционно:

1. Существующий roster остаётся активным во время разбора.
2. Парсер возвращает `{days, warnings}`.
3. Если валидных дней нет, импорт считается неуспешным.
4. Новые данные заменяют старые только после полной проверки результата.
5. Статус показывает имя файла, число дней и число предупреждений, не создавая новый экран.

Парсер:

- обрабатывает все страницы PDF;
- проверяет период и возрастающую последовательность дат;
- отмечает duty без report time;
- отмечает неизвестные аэропортовые токены только тогда, когда они похожи на IATA-коды в строке маршрута;
- предупреждает о неполном периоде или подозрительно малом числе колонок;
- не маскирует пустой код как успешный roster без предупреждения;
- ограничивает сохраняемый `detail`.

Поскольку layout PDF может меняться, предупреждения не блокируют валидные дни, но полностью пустой или структурно неподдерживаемый документ отклоняется.

## Service worker

Имя основного кэша: `fuel-window-v25`. Все кэши приложения используют префикс `fuel-window-`.

При активации удаляются только устаревшие кэши с этим префиксом. Чужие Cache Storage-записи общего origin не затрагиваются.

Стратегия:

- app shell предварительно кэшируется при установке;
- обычные GET-запросы приложения используют network-first с offline fallback;
- в runtime-кэш попадают только успешные same-origin ответы;
- запись в кэш входит в promise lifecycle события;
- `reminders.ics` продолжает обслуживаться отдельным кэшем приложения;
- ошибка сети без кэшированной копии возвращается как обычная ошибка, а не скрывается чужим ответом.

Обновление:

- новая версия вызывает `SKIP_WAITING`;
- баннер обновления показывается только когда автоматическое применение невозможно;
- `controllerchange` выполняет одну перезагрузку.

## Удаление данных

Кнопка «Удалить» удаляет только:

- `localStorage["fuel-v4"]`;
- legacy IndexedDB `fuel-pdf`;
- кэши с префиксом `fuel-window-`.

Остальные данные origin не затрагиваются. Перед удалением сохраняется существующее подтверждение пользователя.

## Доступность

Без визуального редизайна:

- из viewport удаляются `maximum-scale=1` и `user-scalable=no`;
- панель настроек получает `role="dialog"`, `aria-modal="true"` и доступное имя;
- при открытии фокус переходит на кнопку «Готово»;
- фон становится `inert` и скрывается от screen reader;
- при закрытии фокус возвращается на элемент, открывший настройки;
- Escape закрывает только открытую панель;
- выбранный контекст получает `aria-pressed`;
- выбранный roster-день получает `aria-pressed` и текущая дата — `aria-current="date"`;
- скрытая панель не сохраняет фокус внутри себя.

## Критерии приёмки

1. Опубликованная PWA загружается без ошибок.
2. Во время окна питания главный таймер показывает прошедшее время.
3. Старые локальные данные и backup v1 продолжают работать.
4. Повреждённый backup не может сломать следующий запуск.
5. Удаление Fuel Window не удаляет данные или кэши соседних Pages-приложений.
6. Исходный PDF не сохраняется после импорта.
7. Неуспешный импорт не уничтожает предыдущий roster.
8. Offline-запуск работает после первой успешной загрузки.
9. Настройки корректно управляют фокусом и screen reader.
10. README соответствует реализованному приложению.
11. Все автоматические тесты и CI проходят.
